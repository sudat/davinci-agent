## 1. 利用者像と製品の責任

suda さんは編集技術を説明できる人を前提としない。利用者は次のことができる。

- 「なんか映画っぽくない」「絵面が素人っぽい」「ここ退屈」と感想を述べる。
- 見本を見て「近い」「違う」「前の方がいい」と判断する。理由を説明できない場合もある。
- 公開したいと思えるかを判断する。
- 複数チャンネル、複数スタイル、YouTube 本編や TikTok 用の動画を使い分けたいと考える。

色調整、字幕の数値、構図、編集点、音響処理、出力設定、素材探索の方法を利用者に要求しない。
「原因を特定し、実現可能な改善案を作り、映像で示す」ことは製品の責任である。
コーディングエージェントが会話内で編集案を手作業で作って代行しても、製品実装の完了にはならない。

成功の定義: 感想のまま入力して、技術的な言い直しをせず、実際に変わった映像を判断できること。
視聴者の満足や再生数の向上を AI が保証してはならない。利用者の公開可否判断と、公開後の視聴者反応を分ける。

## 2. 製品上の必須ルール

1. 感想を有効な入力として受理する。「具体的な編集命令に言い換えて」を標準の返答にしない。
2. 「映画風＝暗くする・黒帯」「退屈＝短くする」の固定対応を作らない。
3. 原因は仮説として扱い、見た映像・聞いた音・読んだ文などの根拠と区別する。
4. 見た目を調べるときは実フレーム、テンポや音を調べるときは時間を持つ映像・音を確認する。文字起こしだけで観測済みとしない。
5. 理由の入力は任意。「両方違う」「違いが分からない」「任せる」「前に戻す」を成功する操作として用意する。
6. 画像・試作品を選んだことを、無関係な色・音・構成の好みへ広げない。
7. 試作品を作る許可、今回採用する判断、今後のスタイル保存、公開の許可を分離する。
8. 画像生成は既定OFFの任意補助。好みが未確定の初回も生成なしで相談・試し編集へ進める。生成・A/B比較・再生成は§8.8の明示許可範囲のみで行う。
9. 変更していないものを「修正済み」と表示しない。実行できない要望は理由と実行可能な代案を返す。
10. 利用者が Resolve を直接操作しなくても進めることを目指す。同時に、納品物を Resolve で編集できる既存の受入条件を守る。

## 3. 標準の操作の流れ

### 3.1 初回の準備

チャンネル名と、誰に何を届けたいかを短く聞く。利用者が分からない項目は未指定でよい。
参考画像・動画は任意。全素材のタグ付け、事前の長いプロンプト、スタイルの数値入力を要求しない。
既存の承認済み見本があれば提示する。ただし公開可能だっただけの作品を「理想のスタイル」に昇格しない。
スタイルを探す場合だけ、実素材で違いの分かる少数の案を提示する。

### 3.2 普段の制作

1. 素材を置く。画面で素材フォルダを選択するか、事前指定した受け取り先から対象を選ぶ。
2. チャンネル、使うスタイル、届け先を選ぶ。前回値を表示して再利用できる。
3. 今回の希望を一言伝える。チャンネル等の既知の情報で開始できれば空欄も許容する。素材から推測した主題は提案として返す。
4. 「いつもの○○を使い、今回は音楽を控えめにします」のように今回の条件を短く表示する。
5. 素材を確認し、§9.1の予算内で編集前の方向性を相談する。構成や見た目の認識を合わせる必要があれば、§8の絵コンテで「どの場面を、どう見せるか」を示す。方針の採用または明示的な「任せる」の範囲を確認して試作へ進む。「素材を確認中」「冒頭の試し編集を作成中」「今は操作不要」を表示する。未計測の残り時間を捏造しない。
6. 必要な場合だけ短い見本を返す。通常は最初の粗い全編まで進められる。
7. 感想で修正し、変更部分を確認して採用する。最後に全編の公開可否を判断する。

フォルダ監視の常駐機能は初期工程の必須にしない。まずフォルダ選択から実処理を通す。
ブラウザのフォルダドロップで絶対パスが得られると仮定しない。コピー途中の素材を完成扱いしない。

### 3.3 感想による修正

例: 再生中に「ここ退屈」と送信する。

製品は周辺と全体の構成を確認し、「同じ説明が続いているのが原因かもしれません。完成場面を先に見せる案を試しました」と短い試作品を返す。
利用者が「前よりいい。でもせわしない」と言えば、先ほどの案とその返答を踏まえて再調整する。
全体への感想は再生位置を必須にしない。再生位置があるだけで、全体への不満をその一点の修正と断定しない。
対象を特定できなければ候補場面を見せる。利用者に秒数や素材名を探させない。

原因が明白なら推奨する試作品を一つ、判断が分かれるときだけ最大二つを提示する。
「両方違う」なら原因の仮説を見直す。同じ案を表現だけ変えて再提示し続けない。
初期の自動試作予算は一依頼につき二案までとし、追加は利用者の反応または明示的な追加試作で開始する。時間・費用の上限も設定し記録する。

### 3.4 合意したUIの方向性（2026-09-07追記）

ユーザーが確認した4枚のGPT-Image見本は操作の方向性への合意であり、正式な画面デザイン・文言・配置の確定ではない。既存の `cockpit/DESIGN.md` に沿って実画面で磨き込む。見本番号は実装工程番号ではない。

| 利用段階 | 画面の中心 | 利用者の操作 |
|---|---|---|
| 1 素材と希望 | 素材選択、短い希望、任意の参考・チャンネル・既定値 | 素材を選び、希望をひとこと伝える |
| 2 方針相談 | 根拠付き一案または最大二案、必要な短い見本、未確認範囲 | 採用・修正コメント・両方違う・範囲付きの任せる |
| 3 試し編集と対話 | 動画再生、変更前後、感想、確認事実と仮説、変更点 | 理由や秒数を強制されず話し、変更を採用または戻す |
| 4 完成確認 | 仕上げ後の全編、確認結果、今回の完成判断 | 完成版を受け取る。今後のスタイル保存と公開は別操作 |

同じエピソードの文脈で相談・修正・仕上げを往復できる。高度な設定や内部ログは折りたたみ、主画面には今見る映像、今判断すること、次の操作を置く。白地・青い主操作・読みやすい日本語・単一列を既存規約に合わせる。見本の装飾や固定寸法をそのまま実装する義務はない。全待機段階に§3.5の進捗を表示する。

ローカル参考: `private/ux-concepts/2026-09-07-direction-consultation/` の `01-intake.png`、`02-direction.png`、`03-review.png`、`04-finish.png` と `prompts.md`。他環境に画像が無くても本節を実装契約として使える。架空素材・架空確認結果を製品の証拠に転用しない。

### 3.5 待っている間の進捗と異常の見分け方（必須）

素材受付・確認、方針生成、見本、全編試し編集、修正・復帰、仕上げの全待機経路に適用する。回転表示だけで長時間待たせない。KISS・YAGNIにより既存の実行記録・状態取得・予算制御へ接続し、架空進捗や別のジョブ管理基盤を作らない。以下の秒数はUIの初期受入目標であり、処理完了時間の保証ではない。

- 操作から1秒以内に「送信中」等の反応を表示する。受付確認前は開始済みにせず、応答不明時に別ジョブを勝手に作らない。重複送信を防ぐ。
- 10秒を超える待機では、現在の作業、完了済みと次の段階、経過時間、最後の実進捗、利用者の操作要否を表示する。長時間処理が見込まれる場合は最初から表示する。
- 表示例: 「素材を確認中」「24本中8本を確認」「開始から2分10秒」「最後に作業が進んだのは12秒前」「今は操作不要」。件数は実測できる場合のみ。未計測なら「この工程の進み具合は取得できません」とする。
- 素材→方針相談→試し編集→完成確認の利用段階と、現在の具体作業を併記する。完了・現在・未着手を文字でも区別する。段階数や経過時間から全体の百分率を捏造しない。
- 全体と現在工程の経過時間、状態取得時刻、処理担当からの動作報告時刻、成果が進んだ時刻を区別する。時計が増える・APIに接続できるだけでは作業が進んだ証拠にならない。取得不能は不明とする。
- 残り時間は同等条件の測定根拠がある場合だけ幅と推定表示を付け、無ければ「残り時間はまだ分かりません」。
- 「開始待ち」「処理中」「あなたの確認待ち」「再試行中」「状態を確認できない」「停止要求中」「停止済み」「失敗」「完了」を既存状態から区別する。確認待ち・失敗で回転表示を続けない。
- 表示中は原則5秒以内の間隔で状態更新を試みる。通信失敗は直ちに表示し、取得した状態が15秒以上古ければ「状態の更新が途切れています」と最終確認時刻を示す。これは処理停止の断定ではない。裏タブから戻ったら再照会する。
- 画面とサーバーの通信断、処理担当の応答なし、応答はあるが成果が進まない状態を分ける。動作報告の間隔・進捗停滞の判定値は工程ごとに既存timeoutと実測から実装前に固定する。長い外部呼出中など内訳不明ならその旨を示し、正常と保証しない。
- 再試行は理由、同じ工程の何回目か、最大回数、次の動作を表示する。同一工程・同一入力の反復を履歴で確認でき、再試行で累計時間・費用をリセットしない。回数・予算・timeoutの上限で停止し、無限ループを続けない。
- 停滞の可能性があれば最後の進捗と経過を示し、状態の再確認・安全な中止など実行可能な操作を出す。原因未確定を「バグ」や「正常」と断定しない。
- 中止可能な経路には中止操作を用意する。中止要求と実際の停止を分け、即時停止できない外部処理は制約と継続し得る費用を表示する。再実行は対象run・再送安全性・単一Writerを守る。UsageLimit解除・迂回の操作を作らない。
- 完了は今回の対象run・対象版の必要処理成功と利用可能な成果物の確認後だけ表示する。過去runの成功や受付成功を今回の完了にしない。「試し編集を見る」等へ切り替える。
- 再読込・再接続で同じrunへ戻り、完了済み工程・再試行回数・失敗理由・未回答を復元する。画面を離れた場合の処理継続・停止も実際の挙動に合わせ案内する。
- 色や動きだけに頼らず日本語で状態を示す。状態変化は支援技術へ通知し、秒単位の時計を毎回読み上げない。狭い画面でも動画・会話・進捗・主要操作が欠けない。

## 5. 設計: 感想から実際の編集につなぐ

適用原則: KISS（既存の流れを小さく接続する）、YAGNI（必要な実素材のケースだけから拡張する）。DRY による統合は、同じ動作だと試験で示せる場合だけ行う。

### 5.1 責任の分割

```text
利用者の感想 + 現在表示中の版 + チャンネル/スタイル/届け先
  → 依頼の種類と対象を判断
  → 必要な素材・編集済み映像・音を確認
  → 根拠付きの原因仮説と改善案
  → 実行能力/ロック/素材範囲/予算を検証
  → 未採用の試作品を生成
  → 利用者が比較・採用・却下
  → 採用版を更新し、同じ編集情報からResolveへ反映・検証
```

- 具体的命令: 「この字幕を○○に」「この区間を削除」は既存の安全な直接経路を使える。
- 感想・目標: 「退屈」「素人っぽい」「映画っぽく」は原因調査へ送る。規則に一致しただけで調査を省略しない。
- 比較への反応: 「B」「両方違う」「さっきより良い」は現在の提案集合と版に結び付ける。
- 保存指示: 「このチャンネルでは今後も」は今回の編集とは別の保存操作へ送る。
- 一文に複数の意図がある場合は保持する。一部を実行できないときは黙って落とさず、実行する部分と残る部分を示す。

意味判断は既存 Editorial Director / Review 解釈 / 映像確認ロールの役割を整理して担わせる。
同じ素材について複数の AI が独立に最終編集を確定する構造を作らない。
時刻変換、尺、配置、検証、保存、再実行はコードの責任。LLM には検証前の書込権限を与えない。

### 5.2 原因調査と提案に必要な情報

新しい正本 artifact 族を作る指示ではない。既存の提案・レビュー・設定の格納先に対応付け、追加が必要なフィールドと後方互換を工程0で決める。

| 情報 | 必須の意味 |
|---|---|
| 対象 | episode、表示中の版、全体か区間か、既存の正準時間座標への対応 |
| 元の発言 | 利用者の原文。AIの要約で置換しない |
| 観測 | 確認した映像/音/文字の参照、区間、確認方法。未確認部分 |
| 原因仮説 | 何が不満に関係する可能性があるか。観測事実と分離 |
| 提案 | 変更する内容、期待する違い、保持する条件、実行可能性 |
| 試作品 | 元版、提案ID、使用設定、完成/失敗/未確認、比較用の参照 |
| 判断 | 採用/却下/不明/任せる、任意の理由、判断した版 |

AI の確信度を品質の証明にしない。画面では根拠と変更結果を短く示す。
素材にない映像は発見したことにしない。編集では解決できない場合は代案を先に示し、追加撮影は必要性が分かる言葉で提案する。

### 5.3 試作と採用の安全な境界

- 「試作開始可能」と「採用済み」を分ける。既存 Job State Machine と artifact の版管理を使い、二つ目の正本状態機械を作らない。
- 試作は採用版から派生した再生成可能な成果物とする。試作だけで採用済み計画・納品Timeline・公開状態を更新しない。
- 採用処理はサーバーが保存した提案と元版を照合する。ブラウザが返した命令本文やハッシュだけを採用権限の根拠にしない。
- 試作中に採用版が変わったら、古い案を無条件で適用しない。競合を検出し、再試作または再確認にする。
- 同じ送信・採用・再実行は二重適用しない。複数修正の採用前に全体を検証し、失敗時に半分だけ採用済みにしない。
- 取り消しは以前の採用版への新しい復帰操作として履歴を残す。過去の正本を破壊しない。
- 中断・再起動後に、採用版、試作品、未回答の判断、失敗理由を復元する。
- Resolve と Job State は単一 Writer。試作を並行計算しても、採用・Resolve 操作は直列にする。
- 手作業後の `automation_frozen`、ロック、未保存のユーザー編集を尊重する。

### 5.4 入出力・保存先の改修境界

工程0で下記の対応表を実コードの定義・呼び出し元・試験名で埋めてから変更する。これを飛ばして画面だけ先に完成させない。

| 既存の入口/記録 | 追加する意味 | 互換・検証 |
|---|---|---|
| `EpisodeCreateRequest` → `create_episode` → `IntakeRecordV1` → runner | チャンネル、スタイル版、届け先、今回の希望 | 既存のフォルダ＋説明による作成も継続。指定した条件が runner まで届く試験 |
| `ReviewChatRequest` / `ReviewChatEntry` | 表示中の版、出力の識別、提案への返答、必要なら全体/区間 | 古い text＋at_seconds を受けられる。版・チャンネルをサーバー側で照合 |
| `ReviewCommandDraft` と提案の保存経路 | 原文、観測への参照、仮説、実行できる変更、未対応部分 | 命令へ変換できない仮説を実行命令として保存しない |
| `review_apply.py` / 既存 commit 経路 | 保存済み提案の採用、版の照合、重複防止 | 任意のブラウザ本文を実行しない。旧修正経路の回帰試験 |
| 既存 artifact/preview 格納と一覧 | 未採用試作の識別、元版、比較、生成状態 | 試作品と採用版を区別し、再起動して復元 |
| 既存 reference/profile/設定格納 | チャンネルで区切ったスタイル版と明示的な保存履歴 | browser storage を正本にしない。旧記録を破壊しない |

上表は概念上必要な情報であり、列ごとに新規ファイルやモデルを作る指定ではない。
既存の厳格な入力型は未知フィールドを拒否するため、Python型、API変換、TypeScript型、画面、保存・読出しを同じ契約で変更する。
保存形式を変えるなら既存版を読めることを示す。データ移行を伴う場合はバックアップ・復帰手順を記録し、破壊的移行を本書の通常工程に含めない。
新しい操作用入口が必要なら既存の episode-scoped API に限定して設計し、工程0で入力・応答・エラーを確定する。全サービス共通の新しい通信層は作らない。

## 6. 設計: チャンネル・スタイル・届け先の保存

### 6.1 保存単位

| 単位 | 保存する内容 | 勝手に行わないこと |
|---|---|---|
| チャンネル | 対象視聴者、目的、既定スタイル、利用する届け先 | 他チャンネルの修正を混ぜる |
| スタイル | 採用した見本、要素別の好き/避けたい、再現設定、根拠、版 | 生成画像だけから実現済みとする |
| 届け先 | 投稿先と動画種別、画面形状、表示配置、編集方針、検証条件 | 投稿先だけで全作品のテンポを固定する |
| 今回の条件 | 今回だけの希望、選択したスタイル版、出力別の条件 | 次回へ黙って伝播する |

創作上の優先順位は「今回の明示指示 → 選択スタイル → チャンネル既定 → システム既定」。
ロック、権利・安全条件、素材の実現可能性、出力の必須制約はこの順位で上書きしない。衝突は可視化する。
全利用者・全チャンネル共通の好みは初期には自動作成しない。

### 6.2 保存と読出しの規則

- 長い会話履歴を唯一の記憶にしない。既存の保存機構を正本にして、今回必要な要点と少数の見本を取り出す。
- 「Bが好き、理由は分からない」は選択事実として保存可能。色・構図・音などの好みの理由は未確定とする。
- 「今回採用」と「今後のスタイルへ保存」を分ける。「今回だけ」を既定にし、保存操作を画面に用意する。
- 保存時は変わる要素、対象チャンネル、名前を表示する。既存版を消さず更新前に戻せる。
- スタイル更新は進行中のエピソードへ自動適用しない。開始時に使った版を記録する。
- ブラウザ内だけの保存を製品の正本にしない。再読込・別セッションでの復元まで確認する。
- 要点の自動要約は元の選択・発言への参照を保ち、根拠のない好みを追加しない。
- 既存の公開承認済みデータを初期移行する場合、承認の対象範囲を保持し、不明は不明のままにする。

## 7. 設計: 複数フォーマット

初期は「実際に使用する横の本編一つ → 同じ素材から縦の短い動画一つ」の順で証明する。全投稿先・全ジャンルの汎用対応は作らない。

- 出力ごとに主題、冒頭、選択区間、順序、字幕、構図、音の方針を持てるようにする。横動画の切り抜きだけを縦版完成としない。
- 元素材・分析結果は再利用できる。一方、編集案と採用判断と品質検証は出力ごとに分離する。
- 横版の承認は縦版の承認ではない。横版の修正を縦版へ自動伝播させない。
- 同じ Timeline IR を各出力の Preview / Resolve で共有する原則を保つ。出力別の版・時間対応を明示する。
- タイムライン解像度、Compiler、字幕・テロップ配置、構図、書出し、QC の固定値を探索する。UI の縦型選択だけ追加して終わらない。
- 顔や重要な対象の見切れ、字幕の欠け、実際の端末での読みやすさ、音、尺、出力条件を検証する。
- 投稿先の最新制限は実装時に公式資料で確認して根拠と確認日を記録する。本書の例示から秒数・解像度上限を推測しない。
- 縦の切り取りが成立しない素材は、余白つき配置などの実現可能な見本を返す。素材内容を捏造して補わない。

## 8. 設計: 絵コンテによる方向性相談と Codex App Server

### 8.1 役割と証拠境界

絵コンテは、全編を作る前に利用者と「どの流れ・どの見た目で試すか」を合わせ、説明の言い直しと作り直しを減らすための相談手段である。Codex App Serverの画像生成を、撮影素材に基づく構図・色・字幕等の見本作成に使う。構成の提案とコマの順序も合わせて示すが、画像生成処理に物語の事実や編集計画を独自に確定させない。面白さ・音・テンポの確認は実際の短い動画を使う。
画像生成処理に最終編集判断・採用・Resolve 書込の権限を与えない。
生成画像は「見た目の提案」、実編集から取り出した画像は「実際の編集結果」と識別する。
人物・物・出来事を生成で変えた見本を、撮影素材で再現可能と表示しない。

2026-09-07 の調査では、ローカル `codex-cli 0.153.4` が生成する App Server の通信仕様に `imageGeneration` 結果と `savedPath`、画像生成能力の照会項目があった。
これは通信上の定義の確認であり、当該アカウントでの生成成功・複数枚同時生成・速度・利用枠の実測ではない。
公式資料では Codex 組込画像生成と Image API の複数枚指定が案内されているが、両経路を同じものとして実装しない。

- [Codex/App の画像生成](https://learn.chatgpt.com/docs/image-generation)
- [App Server](https://learn.chatgpt.com/docs/app-server)
- [Image API](https://developers.openai.com/api/docs/guides/image-generation)

### 8.2 限定検証

1. 使用バージョン、接続方法、画像生成能力、認証方式を秘密値なしで確認する。
2. 合意済みの見本と実素材の三場面を入力し、三枚を個別に取り出して画面へ返す。
3. 「二枚目の字幕だけ小さく」を実行し、他の場面・選択状態が保たれるか確認する。
4. 保存先だけでなく、実ファイルの存在・表示・画像内容を確認する。
5. 失敗、中断、再接続、枚数不足、重複結果を試験する。成功分を保ち、失敗分だけ再実行できるようにする。
6. 所要時間、実際の枚数、確認可能な利用量、操作回数を記録する。計測できない費用は推定と明記する。

画面上の「まとめて作成」は、内部の複数処理で実現してよい。一回の自然言語依頼で必ず指定枚数が返ると仮定しない。
初期は直列生成を基準にし、同時処理は対応と利用枠を実測した場合だけ制限付きで導入する。
画像APIへの切替は認証・課金が変わるため、無断の代替経路にしない。
画像生成が使えない場合も、既存の実編集プレビューで主経路を続けられる設計にする。
字幕の正確な書体・改行・配置の最終確認は、実際の字幕描画で行う。

### 8.3 利用場面と省略条件（実装前に固定するUX契約）

本節から§8.7は画像の取得実験とは別の製品要件であり、工程2.5の設計・実装前に使う。画面の寸法・装飾、生成速度、同時実行数は実画面と実測で詰めるが、利用目的・操作の意味・採用範囲は後回しにしない。

| 場面 | 絵コンテで判断すること | 次へ渡すもの |
|---|---|---|
| 編集前の方向性相談 | 冒頭で何を見せ、何を伝え、どこへ着地するか。代表場面の見た目が希望に近いか | 今回試す構成・場面・表現方針と未確認部分 |
| 「映画っぽく」「素人っぽい」等の見た目の修正 | 実映像で確認した問題に対し、何を変えると近づくか | 対象場面と変更要素、保持する要素 |
| 「退屈」「せわしない」等の時間・音の修正 | 絵コンテだけでは判定しない。場面の入替え説明には使える | 音付きの短い実編集プレビューで確かめる仮説 |

一案を基本とし、意味のある違いを判断するときだけ最大二案。初期は一案につき代表場面最大三コマとする。三コマは三つの代替案ではなく、一つの方針に含まれる場面の並びである。三コマで全編の確認が済んだとは表示しない。単一場面の修正なら一コマでよく、毎回三枚を埋めない。

既知のスタイルと今回の委任範囲が一致し、方向性に迷いがなければ生成・比較を省略できる。「いつもの方向で任せる」「画像なしで進める」を選べる。利用者が絵コンテを求めた場合は予算・能力の範囲で提示し、使えなければ理由と代わりの確認手段を示す。文章や実フレームで代替したものを「生成絵コンテ完成」と呼ばない。

### 8.4 表示と自然言語での修正

- 同じ相談画面で、案ごとの一文の狙い、場面順のコマ、未確認部分、次の操作を示す。各コマに「冒頭で完成を見せる」等の役割、元の撮影場面への参照、変える点・残す点を付ける。素材名や秒数を利用者に探させない。
- 元素材の切り出しは「撮影素材」、生成した見本は「生成した見た目の案」、実際に編集した結果は「試し編集」と文字で区別する。生成案から元の場面を開いて比較できる。確認用フレームの抽出と絵コンテ生成は別処理であり、前者の実装を後者の完成に数えない。
- 「二枚目の字幕だけ小さく」「冒頭はB、残りはA」「構成はこのまま、色だけ変えて」のような自然な指示を受ける。対象が曖昧なときだけ候補を示して短く確認する。複数要素の選択は一つの新しい方針へまとめ、素材・構成の整合を再検証してから提示する。
- 一コマの変更で、他のコマ・選択済み方針を勝手に変えない。連続性等で他コマの修正が必要なら、影響を先に説明する。画像編集が要求外の人物・物・色等まで変えた場合も差分を確認し、部分修正に成功したと偽らない。旧版へ戻せるようにする。
- 「この方向で試す」「ここを直して」「どちらも違う」「違いが分からない」「画像なしで進める」を理由任意で扱う。「違いが分からない」なら違いを平易に示し、意味のある差がなければ一案に戻す。「どちらも違う」なら仮説へ戻り、却下案を好みとして保存しない。
- 実フレームの確認範囲、生成案の意図、実現可能性の未確認を分ける。素材にない人物・物・出来事を含む案は、そのまま撮影済みの場面や実現可能な編集として採用経路へ流さない。素材で作れる代案を提示する。

### 8.5 絵コンテから実編集への引き渡し

「この方向で試す」は今回の方針と試作範囲への判断であり、完成映像の承認ではない。例えば「構成と字幕の位置はこの案、色は未確認」と要素別の範囲を保持する。画像の選択だけから音・テンポの好み、チャンネルの恒久設定、生成画像を完成動画へ挿入する許可を推測しない。

画像そのものを実行命令の正本にしない。既存の提案・判断記録に、episode/出力/元版、案とコマの識別、元素材参照、生成画像の参照と版、変更指示、採用した構成・表現条件、保持条件、未確認範囲を対応付ける。コマ番号だけに依存せず、並び替え・一枚修正・再読込後も同じ対象を識別する。KISS・YAGNIに従い、絵コンテ専用の汎用基盤や新規正本型を増やさない。

採用した方針は既存Story→Moment→Creativeと検証済み編集経路へ渡し、対応する実素材の短い試し編集を返す。生成画像をそのまま動画として納品しない。利用者に同じ方針をもう一度入力させず、「選んだ案」と「実際の試し編集」を対応付けて比較できることを完了条件とする。素材や編集能力の制約で再現できない要素は黙って外さず、差と代案を示して相談へ戻る。

方針の修正・取り消し・再起動には§5.3の版照合と復元を適用する。生成中に元版が変わった場合、古い結果を現在の選択へ上書きしない。絵コンテだけで音・テンポ・最終字幕・公開可否を確認済みにしない。

### 8.6 待ち時間・失敗と効果の確認

§3.5の待機表示、§9.1の累計時間・費用・呼出上限を絵コンテ生成にも適用する。画像の枚数上限と、短い見本動画の合計30秒上限は別に数える。画像と動画の処理を同じ相談の予算へ合算し、再生成・再試行でも累計をリセットしない。次の生成前に残予算を確認する。

完成したコマから個別に表示し、「三枚中二枚できました。残り一枚は失敗」と実件数を示す。不足分の再試行、完成分だけで判断、画像なしで続行、中止を実際の対応範囲で選べるようにする。失敗分の再試行で成功画像や利用者の選択を消さない。未回答・生成途中・失敗・選択範囲は再接続後も戻る。

合否は画像枚数だけで決めない。§10.2で、絵コンテあり／文章・実フレームのみの相談を同等条件で比較し、利用者の判断時間、機械の待ち時間、言い直し、実編集後の方向違いによる作り直し、本人の「判断しやすかったか」を別々に記録する。比較試験は許可された予算内で行い、事前に評価条件を固定する。負担が増える場面では省略・提示範囲縮小を見直し、画像がきれいという理由だけでUX改善としない。生成画像の表示時刻を実動画のTTFRPに数えない。

### 8.7 画像生成を選んだ場合の任意の往復（2026-09-08追加）

目的は、利用者が完成映像を頭の中で正確に想像したり、編集用語で仕様を書いたりしなくても、生成した加工見本への反応から意図を具体化し、全編を作った後の大きな手戻りを減らすことである。以下は独立機能の一覧ではなく、同じ相談・素材・方針版を引き継ぐ一つの製品経路とする。画像生成はCodex App Server経由の加工提案に用い、撮影済みの場面を架空の風景で置換する用途にはしない。

代表入力（利用者の原文）:

> 今回の動画は落ち着いた感じでありつつ、ロケーションが変わった時に大きなテロップで場面転換があったことを示したい。

| 段階 | 製品が行うこと | 利用者の判断・次への引き継ぎ |
|---|---|---|
| 1 希望と素材の確認 | 実動画から通常場面と場所が変わる場面の代表画像を切り出す。「通常は落ち着く」「場所が変わる時だけ大きなテロップ」を別条件として示す | 利用者は必要な場合だけ場面・解釈を訂正。全素材の手動選定を要求しない |
| 2 同じ素材へのA/B加工案 | 同じ切り出し画像を入力に、構図・文字・色等の違いが判断できる二案を生成し、「どちらが好みに近いですか」と短く聞く | 理由任意で選択・修正・却下。撮影場所や被写体の違いを加工の好みと混同しない |
| 3 要素を混ぜて修正 | 「A案がいいけどB案のフォントは好み。あと背景はもっと暗くして」を、Aの未変更部分＋Bの文字の見せ方＋背景の調整という新しい方針へまとめる | 何を取り入れ、何を保つかを表示。A/Bの丸ごと二択に閉じ込めず、原文と選択元の対応を保持 |
| 4 複数シーンの静止画で確認 | 統合した方針を各シーンの切り出し画像へ適用した生成見本に展開。通常場面、場所が変わる場面、明暗の異なる場面を予算内で代表させる | 一場面で好みが合うだけでなく、複数場面でも意図どおりか判断。気になるコマや要素だけ再修正 |
| 5 サンプル動画で確認 | 静止画段階が問題ないと判断されたら、同じ方針を実素材の短い試し編集へ反映。場所変更の前後と通常場面を含める | テロップの動き・表示時間・場面のつながり・音を確認し、部分修正または全編制作へ進む |

この例は見た目の解釈が分かれるためA/B比較を使う。毎回二案や全段階の承認を強制する規則ではない。既知の好み・委任範囲・追加試作許可に従い、不要な比較は省略する。一方、未回答を「静止画は問題なし」と扱わない。静止画への肯定は動画の動き・音への肯定ではない。

#### 意図を落とさないための条件

- 代表画像は当該エピソードの撮影動画から抽出し、その画像を元に加工案を生成する。画像を抽出しただけを加工案生成と呼ばない。場面を選ぶための資料が足りない場合は不足を示し、架空のロケーションや移動を補わない。
- 場所の変更と、同じ場所でのカット変更を区別する。大きなテロップの対象・文言・適用条件と、通常場面の控えめな表現を保持する。場所変更の判定が曖昧な箇所だけ確認し、全カットへ大テロップを適用しない。
- 「背景を暗く」は、文字の背後の帯・周辺だけ・画面全体のどれかで結果が変わる。意図が未確定なら候補画像または一つの短い質問で範囲を確かめる。勝手に夜景や後続シーンまで暗くしない。
- 選んだフォントは、実際に利用可能な書体・使用条件を確認し、見本と実字幕の対応を残す。生成画像内の架空の文字形状を再現可能なフォントと断定しない。必要なら利用可能な書体を通常の字幕描画で重ねて確かめ、代替になる場合は違いを示して判断範囲を更新する。利用者にフォント名や数値設定を調べさせない。
- 全体方針、場所が変わる時の条件、特定シーンだけの例外を既存の提案・設定へ分けて保持する。後の修正で「Aの構成は維持」「夜景は変えない」等を失わず、要素の組合せに矛盾があれば新方針として検証する。画像の選択を説明できない好みへ拡張しない。
- 初期比較、混合案の修正、複数シーンへの展開、サンプル動画は同一相談の累計予算で扱う。最大二案・各最大三コマの表示上限を、無制限再生成の許可にしない。三コマで条件を代表できなければ未確認を残し、追加は残予算と許可の範囲で行う。
- 試し編集は採用した要素に対応する実設定から作り、静止画を動画化しただけのスライドショーで代替しない。見本と再現結果の差は利用者へ示す。未解決の修正を黙って無視して全編へ進めず、解決するか、保留範囲の判断を記録する。

工程2.5の設計では、この一連の入力・原文・選択元・適用条件・例外・実設定・未確認・復元を既存経路へ対応付ける。工程4の完了は§8.2の画像取得に加え、U40〜U43の往復を通すこと。静止画だけで成功した部分と、実動画・本人判断まで成功した部分を分けて報告する。KISS・YAGNIを守り、この例のための汎用ルールエンジンや別の正本型は追加しない。

### 8.8 画像生成を毎回使わない主経路（2026-09-08見直し、target）

本節は§8内の生成開始条件を限定する。絵コンテによる相談と、生成AIによる画像作成を同義にしない。画像生成は既定OFFで、初回・好みが未確定・雰囲気の希望が曖昧という理由だけで起動しない。生成なしでも新しい方針を相談できることを必須とする。

- 標準は「希望と素材の確認→文章・場面順・撮影素材の切り取り画像で相談→必要な代表場面に実際の字幕・色・配置設定を反映した静止画または短い実編集動画→部分修正→全編」。既存の描画・プレビュー経路を再利用する（KISS・YAGNI）。実設定の静止画も未実装なら完成扱いせず、対応する実動画で確認する。方針・条件・例外・採用範囲・復元の契約は生成の有無によらず維持する。
- 生成は利用者が明示的に希望したとき、または必要性・利用枠への負担を説明して了承を得たときだけ使う。「絵コンテを見たい」「落ち着いた感じ」だけを生成許可にしない。通常は一案・必要最小限のコマとし、A/B比較、複数場面への生成展開、再生成・自動再試行を暗黙に連鎖させない。合意した枚数・修正回数の範囲内は再承認不要、超える場合だけ確認する。
- 生成を拒否・省略・失敗・利用上限到達しても、方針と選択を保って生成なしの経路へ戻れる。生成画像・生成画像IDを相談保存、試し編集、全編開始の必須入力にしない。生成OFF時には画像生成サービスを呼ばず、接続・認証を要求せず、毎回生成利用を勧める確認も出さない。音や動きは引き続き実動画で確認する。
- 生成前に残予算・許可範囲を確認し、利用可能な場合は利用枠も表示する。取得できない消費量を正確な残量として作らず、不明と示す。編集に残す利用枠を使い切るまで自動生成しない。Web版、別エージェント、Image APIを利用上限回避や無断の代替先にしない。Web版への切替開発は今回追加しない。
- 画像生成ON時は、画像生成を担当するCodexセッションをLunaで起動することを必須とする。統合担当がAstraでも生成呼出はLuna側へ渡し、Astra自身では代行しない。起動時に実際に選択されたモデルがLunaであることを確認・記録してから生成する。Lunaが利用不能・モデル確認不能なら生成を開始せず理由を示し、生成なしで続行できる。別モデルへの暗黙切替は禁止。これは生成を指示するCodex側のモデル指定であり、画像生成モデル自体の名称をLunaと呼ばない。既存の起動・モデル指定を使う最小差分とし、製品全体のモデルを一律変更しない（KISS・YAGNI）。
- 利用者の追加観測（2026-09-08）では、Lunaによる画像一枚の生成は5時間枠の1%未満で、利用可能と判断された。この判断に基づきON時はLuna起動で利用する。先のAstraのWeb操作約15%、Astra指示下のLunaのWeb操作約7%、AstraからのCodex直接生成約6〜7%は会話・操作・確認込みの少数試行として区別する。追加観測の詳細な測定条件は未確認で、いずれも固定消費率・課金表・将来の保証値にしない。通常プレビューにも描画時間や相談AIの消費はあり、全工程が無消費とは表示しない。

工程2.5は生成なしの相談・方針保持・実試作を先に受け入れる。工程4は任意生成経路として別評価し、生成未接続・未受入を主経路の利用阻害条件にしない。工程順序と現在の工程2の範囲は変えず、常用生成やWeb連携の実装を先行させない。

### 9.1 工程2.5: 編集前の方向性相談

目的は、全編の重い編集を始める前に、少ない待ち時間・費用・人の操作で方向違いを減らすこと。適用原則はKISS・YAGNI。既存の提案、判断イベント、設定、版管理を再利用し、別の正本状態機械や汎用基盤を新設しない。

#### 提案と判断

- 素材・今回の説明・選択済みスタイルを読み、粗い確認を基本に日本語で推奨一案、判断が分かれるときだけ最大二案を提示する。
- 各案に、誰へ何を伝えるか、構成と各部分の狙い、想定尺、候補場面、字幕・音・テンポの方針、参考との対応、使わない主な素材の理由、未確認と不足を持たせる。画面は短い要約を主とし、詳細は必要時に開く。
- 重要場面・結末の有無や発言の意味など、案の成立への影響が大きく未確認な部分だけを予算内で詳しく確認する。must_keep候補だけには限定しない。粗い確認だけで全素材の不存在や不要を断定しない。
- 構成は文章と場面順の絵コンテ、現在の見た目は実フレーム、変更後は実設定の静止画または短い試し編集、音・テンポは音付き映像で示す。§8の生成見本は明示許可時の任意補助とし、実映像確認の証拠にしない。短い見本に必要な字幕・BGMを付けてよいが、全編の仕上げを相談の前提にしない。
- 採用、修正コメント、却下、両方違う、いつもの方向で任せるを理由任意で選べる。無回答は承認でない。既に記録した委任が今回の対象・条件・予算に合えば追加承認待ちを省略できる。未設定の「いつもの」を捏造しない。
- 構成だけ採用して見た目は未確認、といった判断範囲を記録する。今回の方針採用は最終映像の承認、公開、永続スタイル保存を兼ねない。
- 採用済み方針を既存Editorial DirectorのStory→Moment→Creativeへ実際の制約入力として渡す。対応する生成結果と検証を記録し、実現不能なら黙って外さず相談へ戻す。方針変更後は古い案を無条件で再利用しない。
- PLAN_PROPOSED等の既存状態への対応を、定義・呼び出し元・保存・再開処理で確認する。名前が似ているだけで既存の最終計画承認と同一視しない。既存Proposalの格納先、対象版、承認範囲、再送時の扱いを実装前に確定する。

#### 予算と縮退

- 初期上限は一回の相談で最大二案、見本映像は二案合計30秒以内。同一相談の自動再試行・作り直しでも時間・費用の累計をリセットしない。
- 相談までの壁時計上限、費用上限、詳しい確認の区間数・呼出回数上限を、既存設定・実測に基づき実装担当が数値案として報告し、統合レビューで実行前に固定する。未設定を無制限と解釈しない。今回の文書では未実測の数値を性能保証として作らない。
- 費用を直接測れない場合はその旨を表示し、確認可能な料金・呼出上限等から保守的に予算内を保証できる経路だけを使う。保証できない有料処理は開始しない。
- 次の処理の前に残予算を確認する。実行中の処理には既存のtimeout/cancelを使い、キャンセル不能な処理の時間・費用も隠さず記録する。
- 上限到達時は追加処理を止め、確認済みの文章・静止画・完成済み見本を保持する。文章で判断できる構成だけ提示してよい。映像が必要な見た目・音の確認を合格にせず、未確認のまま残す。
- 原因不明でも可逆な小試作で確認できれば、仮説と明示して予算内で進める。意味が変わる曖昧さ、希望の衝突、安全な経路なしの場合はstop_and_ask。専門的な原因説明を利用者へ要求せず、判断可能な選択と影響を示す。
- UsageLimitの解除・迂回・設定変更を禁止する。制限到達時はそのまま停止・報告する。追加試作の指示を受けても利用制限解除の許可とは扱わない。

#### 参考動画と責任

- 「参考動画で確認した特徴」と「今回取り入れる項目」を別に保存する。前者は出典・対象区間・確認方法・未確認範囲、後者は利用者の選択または範囲付き委任と対象版へ結び付ける。
- 冒頭の構造、カットの間隔、字幕の役割、BGM、カメラワーク等を一回の分析で読み解き、利用者が読んで訂正できる日本語で表示する。取得できないURLや見ていない動画から数値や特徴を捏造しない。
- 表示用Markdownを追加の正本にしない。編集・保存は既存の検証済み経路を通す。チャンネルへの継続保存は工程3へ接続し、今回採用から自動保存しない。工程3未完でも今回だけの選択で工程2.5を検証できる。
- 原因探索、実現可能性の確認、見本提示は製品の責任。作品としての採用・公開可否は利用者が判断する。素材不足は代案と必要に応じた追加撮影を提案する。
- 評価実験のmust_keep等の事前凍結は既存の試験契約を守る。日常制作に全素材の事前分類や専門説明を新たに強制しない。

### 9.2 M: 処理時間の独立調査

- 約761分の既存観測と同一runの時刻・ログを読み、受付、待ち行列、素材読込・変換、文字起こし、映像解析、編集判断、試し編集生成、再試行、人の回答待ちを取得可能な範囲で分ける。ASR等を実測前に主因と断定しない。
- 並行工程の所要時間を単純加算せず、開始・終了・重なりと全体の壁時計を示す。欠損は不明、キャッシュ使用や別条件は別記録とする。
- 既存記録が足りない場合は、必要な計測だけを既存の記録経路へ追加し、次の同一runで取得する。高額・長時間の再実行を内訳調査だけのために自動開始しない。
- 受付から相談の提示まで、受付から最初に判断できる映像まで（TTFRP）、利用者の入力・比較・判断時間、承認待ち回数を分けて測る。文字提案をTTFRP達成に数えない。30秒の見本と全編ラフの到達時刻・判断目的も別記録にする。
- 既存TTFRPの定義と過去値を変更せず、新旧で映像の範囲や条件が異なる場合は直接の改善率を出さない。人の回答待ちを全体時間から黙って除かない。
- 完了報告は対象run、取得できた内訳、不明範囲、支配的工程の根拠、次に計測または改善する対象を含める。記録不足なら主因未特定と報告する。

複数エージェントへ委任する場合の規則:

2026-09-07追加の工程2PはFIRST-PUBLISHの使いやすさ・異常可視化の差分とする。進行中の工程2は範囲を変えず完了レビューし、工程2P→工程2.5へ進む。Mの既存記録調査は先行可能で、長時間の再計測完了は2Pの着手条件にしない。工程2.5の相談待機と後続仕上げにも同じ進捗契約を適用する。実装担当は既存状態の定義・生成元・API・画面・関連試験を追い、取得できない情報と必要な最小追加を着手時に報告する。

- 統合担当が工程0の入出力・保存先を確定してから、バックエンド、画面、独立検証へ分ける。
- 一つの担当に「UX全体を改善」だけを渡さない。各依頼に対象、変更禁止、依存、受入ケース、実行コマンドを添える。
- 読取調査は並行可能。共有ツリーの編集・生成・採用・Resolve操作などの副作用は直列。並行実装するなら隔離した作業場所と競合しない担当範囲を使い、統合は直列にする。
- 新規サービス名・正本型・状態機械を担当者が独自に増やさない。必要性を統合担当へ示して既存への対応を決める。
- 各差分は原則一つの責任に絞る。削除・整理は本改修に必要な範囲のみ。250 pure LOC 制約と SIZE_OK 規則を守る。
- 作成者とは別の検証担当が受入条件を確認する。実機試験のための同時GUI操作を禁止する。

自動試験のAI代替は経路・保存・検証の証明用であり、面白さの証明ではない。
画面だけのモック成功を製品完了としない。古い API 入力・保存データの互換も確認する。

U32〜U38は生成応答を試験用に置換しても、実際の提案保存・選択・実編集入力・再読込まで検証する。Codex App Serverでの実生成成功と画像内容の確認は別に実測する。U39は自動試験では計測経路を固定するだけであり、本人によるUX評価は§10.2で行う。

U40〜U43は§8.7の利用者発言を順に送る連続シナリオとして固定する。各段階の単体試験だけで代用せず、実際の保存・混合方針の入力・条件分岐・実字幕設定・動画試作・再読込のつながりを検証する。生成応答の置換で確認した部分は明示し、実素材・実生成・音付き動画を本人が確認する往復は§10.2で別途評価する。

### 10.2 実素材・本人による確認

同じ実素材・同等の依頼で改修前後を比較する。可能な範囲で条件を揃え、揃わない要因を記録する。
本人の感想を誘導して成功扱いにしない。エージェントのなりきり試験は事前確認に限る。

工程2.5は実素材で、方針の提示→選択→実際の試し編集への反映→違えば相談に戻る往復を確認する。文章だけの提案、保存成功、代替AIによる試験だけでは製品合格にしない。予算上限と評価条件は実行前に固定し、未確認を残したまま合格に数えない。

工程4は§8の絵コンテを使う同じ往復を実素材・実生成・本人の操作で確認する。三枚取得の機構試験だけでは合格にしない。U39の比較条件・不足・順序による慣れの影響も記録し、画像の生成時間を足しても判断や作り直しの負担が減ったかを検討する。改善が示せなければ未証明とし、生成を必須の通過点にしない。

記録する数値:

- 利用者が入力・比較・見直しに使った時間。機械の待ち時間は別に記録。
- 言い直し回数、専門的な説明を求められた回数、手で場所を探した回数。
- 試作回数、却下回数、同じ不満が繰り返された回数。
- 「指示が伝わった」「前より良い」「公開したい」の本人の回答。無回答は未確認。
- 何件中何件で、感想から実映像の改善・採用まで到達したか。

必須条件: 技術的な言い直し要求ゼロ、理由入力の強制ゼロ、チャンネル間混入ゼロ、未採用の納品上書きゼロ、無断公開ゼロ。
時間短縮や映像品質は実測値と本人判定を報告する。試験前に都合のよい合格値を捏造せず、定常30分目標を一回の Bootstrap 成功で達成としない。

### 10.3 実行コマンドと証拠

既存環境と設定を確認してから実行。依存の無断追加は禁止。Python は python3/uv、JS/TS は Bun。

```sh
# video-pipeline/ で実行。変更範囲の試験から始める。
uv run ruff check services/episode_cockpit tests/episode_cockpit
uv run basedpyright
uv run pytest tests/episode_cockpit

# cockpit/ で実行。
bun run typecheck
bun run test
bun run build
command -v bun
command -v agent-browser
bun run e2e
```

上記は出発点。変更した editorial / preview / contracts / production_kit 等の lint・試験も追加し、最終統合で必要な全体検査を実行する。
cockpit に lint script がない場合、存在しない `bun run lint` を成功扱いしない。既存の規則に従い未提供を報告する。
E2E は設定・サーバー起動条件を先に読む。画面表示、主要操作、狭い画面、console error を CLI で確認する。
実機試験は対象を限定した試作プロジェクトで行い、ライブ接続・権限・ロックを確認する。通常試験に成功しても skip されたライブ試験は未確認のまま報告する。
実素材・スクリーンショット・生成見本・ログは private 配下で扱う。リポジトリには秘密値や私的素材を含まない結果要約のみ置く。

## 11. 完了報告の形式

各工程の担当者は次を報告する。

1. 完了した工程と、利用者が新しくできること。
2. 変更ファイル、入出力・保存形式の変更、互換性への対応。
3. 実行したコマンド、結果、受入試験ID、実素材での証拠の場所。
4. 機構として確認済みのこと、本人が評価したこと、未確認を分ける。
5. 未対応・失敗・残るリスク。次工程への依存と復帰方法。

「チャットが返答した」「画像が出た」「命令が保存された」「試作品が良さそう」をもって改修全体を完了しない。
最終的な完成単位は、素材投入 → 感想で修正 → 実試作品 → 採用/復帰 → 再開 → 最終映像確認の往復である。
